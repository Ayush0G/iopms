PROJECT PRESENTATION

IOPMS

Intern Operations & Performance Management System

An internal platform that brings attendance, tasks, daily reports,
project submissions and performance reporting into one place.

Java 21Spring Boot 3.4JWT Supabase / PostgreSQLREST + Swagger

Prepared by Ayush Kumar Sahu · for Valen Labs

Opening: "IOPMS replaces scattered spreadsheets and DMs with one system of record for intern operations. Two roles — admin and intern — with strict rules around attendance and feedback."

01 · WHY BUILD IT

The problem

✗

Scattered records

Attendance in spreadsheets, tasks in chats, reports in email — no single source of truth.

✗

Untrusted working hours

Manual hour entries can be wrong or disputed; there is no reliable audit trail.

✗

No structured feedback

Report reviews and deliverable comments are informal and easy to lose.

✗

No consolidated view

An admin needs one click to see an intern's whole month before evaluation.

GOAL One internal web app: interns self-manage their work, admins track and evaluate it — with rules enforced by the server, not by trust.
Talking point: Each pain point maps directly to a module. Emphasise "server-enforced rules" — that's the engineering theme of the project.

04 · ARCHITECTURE

Layered, package-per-feature

Browser — admin.html / intern.html · fetch + Bearer JWT
↓
SecurityConfig → JwtAuthFilter validates token, sets ROLE_ADMIN / ROLE_INTERN
↓
Controllers routing · @Valid · HTTP status codes
↓
Services business rules · @Transactional · ownership checks
↓
Repositories (Spring Data JPA) derived + JPQL queries
↓
Supabase PostgreSQL / H2 DDL constraints enforce invariants

Cross-cutting: GlobalExceptionHandler maps validation → 400, business rules → 400/403/409, unexpected → 500. DTOs are records; enums are stored as VARCHAR.

Point out the one-way dependency: controllers never talk to repositories directly. The service layer is where all business rules live, so they can be unit-tested with Mockito.

05 · SECURITY

Authentication & authorization

1Loginemail + password
2BCrypt verifyhash check, active flag
3JWT issuedHS256, role + user id
4Bearer on every callfilter validates
5Role checksURL + service layer

Two layers of protection

  • /api/admin/** → ADMIN only
  • /api/intern/** → INTERN only
  • Intern-scoped queries take the user id from the token, never from a request parameter

Hardening details

  • BCrypt hashes — plaintext passwords never stored
  • Deactivated accounts rejected even with a valid token
  • JWT_SECRET ≥ 32 bytes; fails fast at startup
  • @Valid on every request body
Emphasise the ownership rule: an intern cannot read or edit another intern's data by guessing an ID — the backend derives identity from the JWT.

06 · MODULE B (DEEP DIVE)

Attendance — rules that cannot be cheated

The rules

  • Check-in / check-out buttons use the server clock only — no client timestamps accepted
  • One open session per intern (service rule + DB partial unique index)
  • End without start is rejected
  • Minutes computed by the backend; monthly totals + incomplete-session detection
  • Admin corrections require a mandatory reason and write an append-only audit row

Why it matters

Time records are the basis of evaluation and stipend decisions. If interns could post their own timestamps, the data would be worthless in a dispute. The audit table answers "who changed this and why?" later.

Intern limitations

No endpoint exists for an intern to edit hours or history — read-only views, two write actions: start and end.

This is the most heavily tested module: 5 Mockito unit tests plus e2e coverage of start/end, audited correction (480 minutes), and 403 role isolation. Mention the partial unique index as defence in depth.

07 · MODULES C–E

The work lifecycle

C

Tasks

  • Admin assigns: title, description, assignee, priority, dates
  • Intern updates progress 0–100% and status
  • Only admin can set COMPLETED or CHANGES_REQUESTED
  • Remarks flow both ways
D

Daily reports

  • One per intern per date — DB unique constraint
  • Tasks, work, time split, progress, challenges, plan, links
  • Admin approves or requests changes with remarks
  • Missing-report listing for a given date
E

Projects

  • Multi-intern assignment, supervisor, timeline
  • Deliverable = repo URL + notes
  • Automatic version numbers per (project, intern)
  • Every submission keeps review comments
DESIGN RULE Interns can only progress and submit; admins own completion and evaluation.
Version history matters: a "CHANGES_REQUESTED" review doesn't overwrite the old submission — the intern submits v2, and both remain visible with their feedback.

09 · DATA MODEL

Eight tables, constraints doing real work

usersadmins + interns, BCrypt hash, role, active flag
attendancesessions, minutes, check-in/out; one open session
attendance_auditappend-only correction log with reason
tasksassignee, priority, status, progress, remarks
daily_reportsunique (intern_id, date)
projectssupervisor, dates, status
project_internsmany-to-many assignment
project_submissionversioned repo links + feedback

Full DDL in schema-postgres.sql. Hibernate ddl-auto=update bootstraps tables on first start; the SQL file is the authoritative human-readable schema.

Call out the two highlighted constraints — they are the invariants of the whole system: one report per day, and every correction recorded.

10 · DATABASE IN PRACTICE

Connecting to Supabase

How it is configured

  • Four environment variables: DB_URL, DB_USER, DB_PASSWORD, JWT_SECRET
  • run-supabase.ps1 sets them and prompts for the password (no secrets in git)
  • No dev profile for Supabase — that profile intentionally uses H2
  • First boot creates the schema and seeds the admin account

Real-world gotcha we solved

Supabase's direct host is IPv6-only — unreachable from most home networks (UnknownHostException).

Solution: transaction pooler — aws-0-ap-northeast-1.pooler.supabase.com:6543, user postgres.<project-ref>, sslmode=require, prepareThreshold=0.

Good interviewer talking point: this wasn't in the brief — it came from actually running the app. Trial-and-error across regions (Mumbai, Singapore) before Tokyo worked.
